# TASK-011 开发提示词

> 将下列“主提示词”整体复制给负责实现 Task 11 的 Codex 或开发 Agent。它要求 Agent 先冻结基线，再按工作包实现、测试和验收；不要只完成视觉稿或局部样式后提前结束。

---

## 主提示词

你正在 `WenShu` 仓库中继续开发文枢 Windows 桌面应用。请完整实施 **TASK-011：桌面应用外壳、信息架构与编辑体验重构**，直到代码、自动化测试、构建、文档和可执行验收证据全部完成。

### 一、开始前必须完成

1. 完整阅读以下文件，不得只读摘要或标题：
   - `README.md`
   - `docs/PROJECT_BASELINE.md`
   - `docs/FUTURE_UI_OPTIMIZATION_PLAN.md`
   - `docs/TASK_009_BASIC_FILE_MANAGEMENT.md`
   - `docs/TASK_009_COMPLETION_REPORT.md`
   - `docs/TASK_010_DOCX_FIND_REPLACE.md`
   - `docs/TASK_010_COMPLETION_REPORT.md`
   - `docs/TASK_011_UI_SHELL_INFORMATION_ARCHITECTURE.md`
   - `docs/TESTING.md`
   - 仓库内适用于当前目录的全部 `AGENTS.md`（如果存在）。
2. 检查 `git status`。保留并绕开用户已有改动，不得重置、覆盖或清理不属于本任务的内容。
3. 阅读现有 renderer 组件、hooks/controller、共享协议、preload、主进程文件管理实现和相关测试，理解稳定 `tabId`、`mutationEpoch`、saving/dirty/conflict、DOCX 伴随备份和路径迁移语义。
4. 在修改产品代码前运行当前基线：
   - `./scripts/npm.cmd run check`
   - `./scripts/npm.cmd run build`
5. 如果基线失败，先判断是否为当前主干问题、环境问题或用户已有改动；记录证据，不得通过弱化断言、跳过测试或扩大容错来掩盖失败。

### 二、任务目标

把当前“功能完整但具有工程原型感”的界面重构为一致、清晰、适合 Windows 桌面长期使用的 Pre-alpha 产品界面，同时保持 Task 1 至 Task 10 的全部产品、安全和生命周期语义。

本任务必须完成：

1. 建立统一的 CSS 设计变量、组件状态和项目内 SVG 图标体系；
2. 消除英文原生菜单与中文应用菜单同时出现的问题，只保留一套语言一致、行为真实的菜单；
3. 删除工作区侧栏左下角的大面积文件操作按钮区；
4. 使用文件树右键菜单、键盘命令和文件树内部拖拽承载文件管理；
5. 支持侧栏调整宽度、折叠、长路径和深层目录；
6. 重做活动栏、标签、保存状态、状态栏和通知反馈；
7. 优化 DOCX 内容列宽、编辑画布和工具栏分组/溢出；
8. 统一 TXT、DOCX、工作区搜索和当前查找的视觉与交互语言；
9. 完成无障碍、Windows 缩放和关键页面视觉基线；
10. 为所有新增交互补齐自动化测试，并通过完整质量门禁。

### 三、不可改变的基线

以下约束优先级高于视觉便利，不得擅自改变：

- Windows 桌面端优先，Electron + React + TypeScript 技术基线不变；
- `nodeIntegration: false`、`contextIsolation: true`、sandbox 和窄 preload/IPC 边界不变；
- renderer 不得直接访问 Node.js 文件系统；
- 不新增通用 invoke、任意路径、force、overwrite、永久删除或任意文件写入能力；
- 文件操作继续使用既有 controller、共享契约和主进程安全服务；
- 路径边界、逐段 symlink/junction、realpath、revision、CAS、临时文件和发布前复验不弱化；
- 删除只进入系统回收站，不提供永久删除降级；
- DOCX `.wenshu.bak` 迁移、失败回滚或 partial failure 语义不变；
- 稳定 `tabId` 与可变路径继续解耦；
- 移动后标签顺序、活动状态、dirty、saving、正文/模型、选区、滚动、撤销历史和当前查找会话保持；
- 成功文件变更继续递增 `mutationEpoch` 并使工作区搜索失效；失败、取消、reveal 不得误递增；
- dirty/saving/conflict/read-only/degraded、关闭保护、窗口关闭和工作区切换语义不变；
- TXT 与 DOCX 查找替换、工作区搜索、结果定位和保存安全不得回归；
- 不得用 DOM 私有属性或编辑器私有 API 绕过现有公开接口；
- 不得记录文档正文、搜索文本、绝对用户路径或敏感内容到日志。

如确实需要改变任一基线，必须在编码前明确说明问题、收益、风险、新增复杂度、迁移成本和影响范围，并等待项目所有者确认。不得静默改变。

### 四、交互要求

#### 4.1 文件树右键菜单

必须至少支持以下上下文：

- 工作区根或空白处：新建 TXT、新建 DOCX、新建文件夹、刷新、在资源管理器中显示；
- 普通文件：打开/激活、重命名、移动到、在资源管理器中显示、删除到回收站；
- 文件夹：在该目录新建 TXT/DOCX/文件夹、重命名、移动到、在资源管理器中显示、删除到回收站；
- 当前文档的保存、另存为和关闭位于文件菜单或标签右键菜单，不再长期显示在文件树底部。

菜单必须满足：

- 根据对象类型、saving 状态和能力正确启用/禁用；
- 使用稳定对象身份和规范相对路径，不从展示文本反解析身份；
- 支持鼠标右键、`Shift+F10` 或菜单键；
- 支持方向键、Enter、Escape、焦点圈定和关闭后焦点恢复；
- 菜单项有明确文字与无障碍名称；
- 危险操作分组置底，不能只靠红色表达风险；
- 点击外部、切换工作区、目标卸载或窗口失焦时安全关闭；
- 不残留全局事件监听、定时器或过期菜单状态。

可优先采用 renderer 内可测试、可访问的菜单实现；如果选择 Electron 原生菜单，必须说明理由，并保持固定命令协议和测试能力，不得为此暴露通用 IPC。

#### 4.2 键盘等价入口

至少支持：

- `Enter`：打开文件或展开/折叠目录；
- `F2`：重命名；
- `Delete`：打开删除确认；
- `Shift+F10` 或菜单键：上下文菜单；
- `F5`：刷新；
- `Ctrl+Shift+S`：另存为当前文档；
- `Escape`：关闭菜单、取消拖拽或退出当前非模态交互。

快捷键不得绕过 saving、dirty、冲突、确认、路径或权限门禁；不得破坏编辑器内已有快捷键语义。

#### 4.3 文件树内部拖拽

本任务只实现同一工作区文件树内部的移动：

- 文件拖到目录；
- 文件夹拖到其他目录；
- 文件或文件夹拖到工作区根投放区；
- 投放后调用既有 `relocate` 流程，不自行执行文件系统操作。

必须处理：

- 可接受目标高亮；
- 非法目标禁止状态；
- 轻量拖拽预览；
- `Escape`、dragend、drop、组件卸载和工作区切换后的完整清理；
- 投放后 pending 状态，防止重复提交；
- 拖到当前位置为无操作；
- 目录到自身/后代、同名目标、非法类型、saving、过期工作区/路径变化的拒绝；
- 主进程最终裁决失败后的稳定错误提示和状态恢复；
- 成功后的稳定 tabId、伴随备份迁移和 mutationEpoch 语义。

不要在本任务实现从 Windows 资源管理器拖入、拖出应用、跨工作区、跨盘、复制或覆盖移动。

### 五、视觉和布局要求

#### 5.1 视觉方向

- 保留文枢克制、安静、适合长时间写作的气质；
- 以中性表面和单一主强调色为主，不使用大面积渐变、玻璃拟态、过度阴影或装饰动画；
- 优先提升信息层级、间距、对比度和状态辨识度，而不是追求炫技；
- 使用项目内 SVG，不用 emoji、单字母或远程图片充当正式功能图标；
- 不为完成本任务引入庞大 UI 框架或图标依赖；如需新增依赖，先证明必要性和体积影响。

#### 5.2 设计变量与组件状态

建立并实际使用：

- 背景、表面、边框、主要/次要文本；
- primary、success、warning、danger、info；
- hover、active、selected、focus-visible、disabled、loading；
- 间距、字号、圆角、阴影、层级、动画时长；
- 高对比度和 `prefers-reduced-motion` 入口。

统一按钮、图标按钮、输入框、选择框、复选框、菜单、tooltip、toast、横幅、空状态、对话框、滚动区和侧栏调整手柄。

不要一次性机械重写全部 CSS。先建立 token 和组件边界，再按工作包迁移；每次迁移都运行相关测试并检查视觉状态。

#### 5.3 应用外壳

- 顶部只保留一套菜单；
- 活动栏使用统一 SVG、tooltip 和无障碍名称；
- 设置入口未实现时不能伪装成可用功能；
- 标签同时表达活动、dirty、saving、错误和关闭能力；
- 保存状态紧凑，不让备份路径长期占据整行；
- 状态栏降低色彩和高度权重，Electron 版本移到“关于”。

#### 5.4 侧栏与编辑区

- 文件树获得取消按钮墙后的完整垂直空间；
- 侧栏宽度可调、可折叠，并有合理最小/最大值；
- DOCX 使用居中、有限最大宽度的内容画布，外围使用工作区背景；
- 不模拟或承诺精确 Word 分页；
- TXT 保持适合纯文本编辑的全高布局；
- DOCX 工具栏按历史、字符格式、段落样式、列表与对齐分组；
- 窄窗口下使用稳定溢出策略，不把编辑区撑出横向滚动。

#### 5.5 搜索与反馈

- 工作区搜索和当前查找共享控件语言，但保持各自语义；
- 搜索结果形成“文件 → 匹配项”层级，片段优先、行列次要；
- 查询说明简化，详细限制通过帮助或可展开说明查看；
- 成功操作使用非阻塞、限时、可关闭的 toast；
- 错误、冲突和部分完成信息可追溯，不自动消失；
- 当前匹配、普通匹配、输入焦点和按钮焦点不能混用同一视觉状态。

### 六、实施顺序

严格按以下工作包推进。每个工作包完成后运行定向测试并记录结果，再进入下一包。

#### WP0：冻结基线

- 形成当前界面状态矩阵；
- 固定 `1280×820`、`900×600` 基线；
- 核对现有 menu、快捷键、焦点、文件管理 controller 和测试假设；
- 必要时编写 WP0 报告，记录技术选择、事件模型、拖拽状态机和风险。

#### WP1：设计变量、图标和基础组件

- 建立 token；
- 按 shell/workspace/document/search/common 拆分样式职责；
- 完成 SVG 图标、按钮、输入、菜单、toast、对话框和焦点基线；
- 不改变业务行为。

#### WP2：应用外壳

- 解决双菜单；
- 重做活动栏、标签、文档状态和状态栏；
- 完成关于入口和运行时信息迁移；
- 保持窗口关闭和快捷键语义。

#### WP3：侧栏、右键和拖拽

- 删除底部按钮区；
- 完成右键菜单和键盘等价入口；
- 完成侧栏调整与折叠；
- 完成内部拖拽移动及安全拒绝路径；
- 补齐 controller、生命周期和无障碍测试。

#### WP4：编辑区和搜索

- DOCX 居中内容画布；
- 工具栏分组与溢出；
- TXT/DOCX 标签和状态统一；
- 工作区搜索、当前查找和反馈层级优化。

#### WP5：验收和文档

- 无障碍、高对比度、减少动画、缩放与最小窗口检查；
- 关键页面截图基线；
- 全量回归、构建、开发与生产冒烟；
- 更新 README、PROJECT_BASELINE、TESTING、Task 11 文档并编写完成报告。

### 七、代码结构要求

- `App.tsx` 只保留必要的顶层编排，避免继续堆积展示细节；
- 按稳定职责抽取 shell、menu、toast、sidebar resize、context menu 和 drag state；
- 不为了减少文件行数而制造无语义的微组件；
- 状态机、路径计算、菜单能力判断和拖拽目标判断优先写成可独立测试的纯函数；
- UI 不复制主进程安全逻辑，只做必要的即时能力判断；
- 全局事件监听必须集中管理并在卸载时清理；
- React key 和交互身份使用稳定 tabId 或规范 relativePath，不使用展示名称；
- 保持严格 TypeScript，不引入 `any`、非必要类型断言或未解释的 `eslint-disable`；
- 不使用私有编辑器 API，不静默吞掉失败。

### 八、测试与质量门禁

必须新增或更新测试覆盖：

1. 各对象类型的右键菜单项、启用状态和命令参数；
2. 菜单键盘导航、Escape、外部点击和焦点恢复；
3. F2、Delete、F5、Ctrl+Shift+S 与编辑器快捷键兼容；
4. 文件/目录拖动、目录/根投放和 pending 防重；
5. 自身、后代、同名、saving、非法类型和迟到结果拒绝；
6. 拖拽取消、卸载和工作区切换无残留；
7. 移动后 stable tabId、编辑器会话、备份和 mutationEpoch 回归；
8. 侧栏最小/最大宽度、折叠和窄窗口布局；
9. 工具栏溢出、标签状态、toast 和搜索层级；
10. 菜单、图标按钮、拖拽目标、toast 和对话框无障碍名称。

不得：

- 删除或弱化 Task 1 至 Task 10 的既有测试；
- 添加无条件 `.skip`、`.only` 或宽泛快照代替行为断言；
- 通过增加超长 timeout 掩盖事件泄漏或竞态；
- 只测试 CSS class 是否存在而不验证关键交互和状态转移。

最终必须依次通过：

- 定向测试；
- `./scripts/npm.cmd run typecheck`
- `./scripts/npm.cmd run lint`
- `./scripts/npm.cmd run format:check`
- `./scripts/npm.cmd test`
- `./scripts/npm.cmd run check`
- `./scripts/npm.cmd run build`
- Windows 开发模式冒烟；
- Windows 生产构建冒烟。

如果视觉测试环境无法可靠自动化真实 Electron 截图，不得伪造通过；应保留确定性组件/布局测试，并提供明确的人工截图步骤、尺寸、缩放比例和结果记录。

### 九、必须人工核对的场景

- `1280×820`、`900×600`；
- Windows 100%、125%、150% 显示缩放；
- 200% 文本缩放、高对比度、减少动画；
- 空工作区、长文件树、深层目录、超长文件名和多标签；
- TXT、DOCX、read-only、degraded、dirty、saving、save-error、conflict；
- 工作区搜索大量结果、截断状态和当前 DOCX 查找替换；
- 鼠标、键盘、右键、内部拖拽和取消；
- 重命名、移动、删除、另存为后的标签与搜索生命周期；
- 窗口关闭、工作区切换和保存中保护。

### 十、明确非目标

不要在 Task 11 中实现：

- 从 Windows 资源管理器拖入或拖出文件；
- 跨工作区、跨盘、复制、覆盖移动或批量操作；
- 自动保存、会话恢复、文件系统监听；
- 深色主题、完整设置系统或主题插件；
- 工作区替换、正则/模糊/语义搜索；
- 复杂 DOCX、精确分页或完整 Word 无损编辑；
- 安装包、自动更新或正式发布；
- AI、Agent、云端或账户功能。

发现相邻需求时记录为后续建议，不要擅自扩大当前实现范围。

### 十一、工作方式

- 先调查再修改，以当前代码和测试为事实来源；
- 制定并持续更新可检查的工作计划；
- 优先小步、可回归的工作包，不做一次性大爆炸重写；
- 每完成一个工作包，报告完成内容、测试证据、剩余风险和下一步；
- 遇到普通实现问题时自行诊断和修复，不把可由代码或测试确定的问题反问用户；
- 只有在需要改变产品基线、扩大权限、加入重大依赖或存在无法合理推断的产品选择时才暂停请求确认；
- 不执行破坏性 Git 操作，不覆盖用户改动，不擅自 push、merge 或发布；
- 在全部验收完成前不要仅以“主要功能已完成”结束任务。

### 十二、最终交付

完成后必须提供：

1. `docs/TASK_011_COMPLETION_REPORT.md`，逐项对应 Task 11 的工作包和完成标准；
2. 更新后的 `README.md`、`docs/PROJECT_BASELINE.md` 和 `docs/TESTING.md`；
3. 关键界面截图或明确可复现的截图基线位置；
4. 新增/修改文件清单及重要架构说明；
5. 所有质量命令的真实结果、用例数量和条件跳过原因；
6. Windows 开发/生产冒烟记录；
7. 已知限制、未解决问题和后续任务建议；
8. 明确说明是否满足 Task 11 全部验收标准，不得把未验证项描述为已完成。

最终回复应先说明实际完成结果，再简要列出关键改动、测试证据、已知限制和重要文件链接。

## 使用建议

- 如果希望一次性完成 Task 11，直接使用上面的完整主提示词。
- 如果希望分工作包开发，应在每次续接时保留主提示词的全部安全基线，并明确当前只执行 `WP0`、`WP1` 等某一工作包；后续 Agent 必须先阅读前序工作包报告和当前 `git diff`。
- UI 实施涉及较多视觉判断。开发者应在 WP0 固定截图与状态矩阵，在 WP1 确立 token 后再批量迁移页面，避免各页面各自形成新的颜色和间距规则。
