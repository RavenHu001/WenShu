## 1. 项目标识

- **暂定产品名：** 文枢
- **英文名：** Wenshu
- **推荐仓库名：** `wenshu-desktop`
- **项目类型：** 本地多文档编辑与管理桌面应用
- **主要平台：** Windows 10 / Windows 11
- **开发模式：** 个人开发者主导，AI Agent 辅助规划、编码、测试和维护

平台目标不等于当前发布声明。Task 12 当前内部二进制完成级别只包含 Windows 10 x64 理论兼容性；
Windows 10 实机验证留到后续开发阶段，Windows 11 验收、可信签名和公开二进制发布均为未来可选工作。

### 1.1 命名含义

“文”代表文档、文字和创作内容；“枢”代表中心、枢纽和统一入口。

该名称对应本项目的核心理念：将多个分散的本地文档集中到一个工作区中，在中央编辑区域完成阅读和编辑，并通过文件树、搜索及后续 AI 能力统一管理。

“文枢 / Wenshu”目前作为项目暂定名。若未来进行公开发布、商业化或品牌注册，应另行完成名称冲突、域名和商标检查。

## 2. 项目概述

文枢是一款面向个人多文档创作和资料管理的轻量级桌面应用。

应用在整体交互方式上参考 Visual Studio Code，采用工作区、文件树、多标签页、中央编辑区和辅助侧栏等结构，但主要处理对象不是源代码，而是普通文本和文档文件。

项目的核心目标是：

> 让用户能够像管理一个代码项目一样，集中管理、搜索、切换和编辑一组相互关联的文档。

项目初期支持 TXT 和基础 DOCX 文件，以简单、稳定、可运行和可继续扩展为主要标准。项目不以完整复制 Microsoft Word 或 Visual Studio Code 为目标。

## 3. 项目定位

### 3.1 产品定位

文枢是一款：

> 面向个人创作、设定整理和资料维护的本地多文档工作台。

主要使用场景包括：

- 世界观、人物、地点、组织和历史设定管理；
- 小说章节和长篇内容管理；
- 游戏设计文档管理；
- 项目说明、研究笔记和个人资料整理；
- 多个相关文档之间的快速切换；
- 工作区级文本搜索；
- 未来通过 AI 辅助理解、整理和修改文档。

### 3.2 非目标

项目初期不定位为：

- Microsoft Word 的完整替代品；
- 专业出版和精确排版软件；
- 在线协作文档平台；
- 云端文件管理系统；
- 企业级知识库；
- 完整集成开发环境；
- 无人监督的 AI 自动化平台。

## 4. 核心设计原则

### 4.1 本地文件优先

- 用户以本地文件夹作为工作区。
- 文件继续保存在普通文件系统中。
- 不强制导入专用数据库或私有文件格式。
- 基础文件管理和编辑功能应能够离线运行。
- 应尽量保证用户可以继续使用其他软件打开原始文件。

### 4.2 中央编辑区优先

中央文件编辑区域是界面的视觉和操作核心，应占据窗口中最大的空间。

左侧负责工作区导航和搜索，右侧用于文档属性、格式设置和未来 AI 辅助。左右侧栏均应允许折叠，使中央区域可以根据需要扩展。

### 4.3 基础功能优先

初期优先完成：

- 工作区打开；
- 文件树浏览；
- 多标签页；
- TXT 编辑；
- 基础 DOCX 阅读与编辑；
- 保存；
- 搜索；
- 基础文件管理；
- 状态恢复。

复杂格式、云端服务、插件系统和完整 Agent 能力不应阻碍基础版本完成。

### 4.4 简单扩展，而不过度设计

项目需要保持清晰的模块边界，为新文件类型和 AI 功能预留接口，但初期不建立复杂的插件框架、微服务体系或大型数据库架构。

### 4.5 数据安全优先

- 保存失败不得清除未保存状态。
- TXT 保存应检查读取版本，外部内容变化时不得静默覆盖。
- TXT 写入应使用目标同目录临时文件，完成写入、刷盘和关闭后再安全替换目标。
- DOCX 保存前应创建备份或安全副本。
- 重要文件写入应优先采用临时文件后替换的方式。
- 删除操作必须确认。
- 单个文件错误不得导致整个应用崩溃。
- AI 不得在用户不知情的情况下覆盖文件。

## 5. 初期功能范围

### 5.1 工作区

应支持：

- 选择本地文件夹作为工作区；
- 显示文件和子文件夹；
- 展开和折叠目录；
- 刷新文件树；
- 记录最近工作区；
- 根据设置恢复上次工作区；
- 检测基本的外部文件变化。

初期只要求单根目录工作区。

### 5.2 文件管理

应支持：

- 新建 TXT 文件；
- 新建基础 DOCX 文件；
- 新建文件夹；
- 打开文件；
- 保存和另存为；
- 重命名；
- 删除；
- 在 Windows 文件资源管理器中显示。

Task 9 已完成基础文件管理闭环（见 [TASK-009 完成报告](../tasks/task-009/TASK_009_COMPLETION_REPORT.md)）：在工作区根或选中文件夹内新建 TXT/基础 DOCX/文件夹（排他创建、不覆盖不自动改名；DOCX 从规范空模型导出并验证）；TXT/DOCX 另存为走两阶段覆盖确认（目标存在第一次只返回受控目标 revision，确认后二次提交携带 `expectedTargetRevision` 做发布前 CAS）；普通文件与目录重命名/移动（含 Windows 只改大小写两步中间名 + 回滚，目录禁止移入自身或后代），DOCX 伴随 `.wenshu.bak` 备份随主文件迁移，失败回滚或明确 partial failure；删除统一调用可注入 `shell.trashItem` 进入 Windows 回收站（严禁永久删除降级），主文件与伴随备份非事务的部分成功返回 `PARTIAL_FAILURE` 并强制刷新；"在资源管理器中显示"在重新校验后调用固定 `showItemInFolder`。所有写操作经固定窄 IPC 与按窗口串行队列，源/目标逐段校验不跟随 symlink/junction；成功操作后标签以稳定 tabId 原地迁移（单文件精确、目录段边界前缀，编辑器会话与 dirty/saving 保持），并递增 `mutationEpoch` 取消活动搜索、清空 completed 结果与定位（失败、取消、reveal 不递增）。

### 5.3 多标签页

应支持：

- 同时打开多个文件；
- 标签页切换；
- 关闭标签页；
- 未保存状态标记；
- 防止同一文件重复打开；
- 关闭未保存文件时进行确认。

### 5.4 TXT 支持

应支持：

- UTF-8 文本读取和保存；
- 基础文本编辑；
- 复制、剪切和粘贴；
- 撤销和重做；
- 当前文件查找和替换；
- 字符数或字数统计；
- 常用快捷键。

### 5.5 DOCX 支持

初期只要求支持基础 DOCX 内容：

- 普通段落；
- 标题；
- 粗体；
- 斜体；
- 下划线；
- 基础字号和文字颜色；
- 项目符号和编号列表；
- 基础文字对齐；
- 简单 DOCX 创建和导出。

初期不承诺完整支持：

- 精确分页；
- 页眉和页脚编辑；
- 脚注和尾注；
- 批注和修订记录；
- SmartArt；
- 宏；
- 公式；
- 高级字段；
- 复杂表格；
- 复杂浮动图片和文本框；
- 与 Microsoft Word 完全无损的格式往返。

复杂 DOCX 可以降级显示、只读打开或在用户确认后进行编辑。

Task 7 已完成（见 [TASK-007：基础 DOCX 阅读、编辑与安全保存](../tasks/task-007/TASK_007_DOCX_BASIC_EDIT_SAFE_SAVE.md) 与 [TASK-007 完成报告](../tasks/task-007/TASK_007_COMPLETION_REPORT.md)）：以有版本、有资源上限的结构化中间模型（`DocxDocumentModel`，见 `src/shared/docx.ts`）衔接 DOCX 导入、Tiptap/ProseMirror 编辑与基础导出；复杂内容按 `supported`、`degraded`、`read-only` 分级处理（`rejected` 为读取错误路径）。覆盖保存执行原始字节 revision 冲突检测、同目录滚动备份 `<文件名>.wenshu.bak`、临时生成、产物重新验证、刷盘、关闭与安全替换。Task 7 不包含新建/另存为、DOCX 搜索、复杂 Word 格式或完整无损往返。

### 5.6 搜索

应支持：

- 当前文件查找；
- 当前文件替换；
- 工作区 TXT 内容搜索；
- 工作区 DOCX 正文搜索；
- 按文件显示匹配结果；
- 点击结果打开对应文件。

Task 6 已完成 TXT 查找与搜索闭环（见 [TASK-006 完成报告](../tasks/task-006/TASK_006_COMPLETION_REPORT.md)）：当前文件查找替换作用于活动编辑器的实时正文（`Ctrl+F` / `Ctrl+H`，普通文字查询、大小写选项、上一个/下一个、替换当前项与全部替换，替换经 CodeMirror 编辑事务进入撤销历史）；工作区 TXT 搜索作用于磁盘已保存内容，通过主进程受控异步遍历、固定并发 4、取消和结果上限（候选 1000 / 单文件 200 / 总匹配 2000）完成。搜索结果以规范相对路径和内容 revision 标识文件，点击后复用多标签的打开/激活能力；revision 或正文范围已失效时只提示结果过期，不错误定位或覆盖内容。Task 6 首版不实现工作区替换、工作区正则搜索、持久全文索引或 DOCX 搜索（DOCX 搜索由 Task 8 完成）。具体实施边界与验收见 [TASK-006 规划](../tasks/task-006/TASK_006_TXT_SEARCH_FIND_REPLACE.md)。

Task 7 仍不把 DOCX 隐式加入 Task 6 的 TXT 搜索器。Task 8 已完成（见 [TASK-008 完成报告](../tasks/task-008/TASK_008_COMPLETION_REPORT.md)）：工作区 DOCX 正文搜索与富文本结果定位复用搜索任务身份、取消、预算和 revision 过期原则，但为 DOCX 单独设计基于结构化模型（`DocxDocumentModel`）的规范正文投影（`src/shared/docx-search-text.ts`，深度优先文本块 + 人工 `\n` 分隔的纯函数）、文本块位置映射与 ProseMirror 公开 API 定位；主进程混合搜索执行总候选 1000（其中 DOCX 200）、总并发 4（其中 DOCX 并发 2）；结果定位必须通过 kind、revision、范围与匹配文本双重校验（App 实时投影校验 + DOCX 宿主同规则投影二次校验），任何过期、结构变化或映射失败只显示非破坏性提示，不错误定位、不修改正文；搜索不写工作区、不建立索引。

Task 10 已完成（见 [TASK-010 完成报告](../tasks/task-010/TASK_010_COMPLETION_REPORT.md)）：当前 DOCX 内查找与替换与 TXT 共用“查找与替换”侧栏入口——DOCX 搜索唯一来源是活动 Tiptap/ProseMirror 实时文档（复用 Task 8 的 `joinDocxTextBlocks` 投影规则，不读磁盘、不搜索模型旧快照或编辑器 DOM）；literal + ASCII 大小写折叠、非重叠、单行与长度规则、最多 2000 匹配（2001+ 截断并禁用全部替换）；普通/当前匹配经项目自有 plugin 的 DecorationSet 双 class 高亮，查找/导航/关闭面板不修改正文、不 dirty、不进撤销历史；替换当前项执行瞬间重新扫描复验实时范围，非空替换继承匹配起点字符 marks（跨不同 marks run 只取起点），全部替换 ≤2000 项逆序写入同一 transaction、一次 undo/redo，dispatch 前对候选 `tr.doc` 执行 `tiptapJsonToDocxModel` + 序列化预算验证（任一失败 0 dispatch、0 dirty）；read-only 可查不可替换，degraded 确认绑定当前 revision 后可替换（重新读取后旧确认失效），saving 期间替换不被旧保存完成清除；每标签状态绑定稳定 tabId，重命名/移动/另存为后会话保持，关闭标签/重开/工作区切换完整清理；工作区结果定位与 mutationEpoch 不污染当前查找状态；无新增 IPC/preload/DesktopApi。

## 6. 界面布局基线

应用采用以中央文件编辑区域为核心的桌面工作台布局。

```text
┌──────────────────────────────────────────────────────────────────┐
│ 菜单栏：文件  编辑  视图  工具  帮助                            │
├──────┬────────────────┬──────────────────────────┬───────────────┤
│活动栏│ 左侧边栏       │ 中央文件编辑区域         │ 右侧辅助栏    │
│      │                │                          │               │
│文件  │ 工作区文件树   │ 编辑器标签页             │ 文档属性      │
│搜索  │ 搜索结果       ├──────────────────────────┤ 格式设置      │
│大纲  │ 文档大纲       │                          │ 文档信息      │
│设置  │ 最近文件       │ 当前文件编辑器           │ AI 面板预留   │
│AI预留│                │                          │               │
├──────┴────────────────┴──────────────────────────┴───────────────┤
│ 状态栏：文件类型、保存状态、字数、光标位置、工作区状态           │
└──────────────────────────────────────────────────────────────────┘
```

### 6.1 中央文件编辑区域

中央区域应：

- 占据默认布局中的最大宽度；
- 包含编辑器标签栏和当前文件编辑器；
- 根据文件类型加载对应编辑器；
- 在左右侧栏折叠时自动扩大；
- 保证窗口缩小时仍具有优先可用空间；
- 为未来分屏编辑保留可能性，但初期不要求实现。

文件类型与编辑器的概念对应关系：

- `.txt` → 纯文本编辑器；
- `.docx` → 富文本编辑器；
- 未来 `.md` → Markdown 编辑器；
- 未来 `.pdf` → 只读预览器；
- 不支持类型 → 文件信息及不支持提示页面。

### 6.2 左侧区域

左侧活动栏用于切换主要功能入口，初期包括：

- 文件；
- 搜索；
- 设置。

文档大纲和 AI 可作为后续入口。

左侧边栏主要显示：

- 工作区文件树；
- 搜索输入与结果；
- 最近文件；
- 未来文档大纲。

### 6.3 右侧辅助栏

右侧辅助栏不是首版必须功能，可以在后续逐步加入。

可用于：

- 文件和文档属性；
- DOCX 格式设置；
- 文档统计和兼容性提示；
- 未来 AI 对话、修改建议和操作确认。

右侧辅助栏应可折叠，不能长期挤压中央编辑区域。

### 6.4 状态栏

状态栏可显示：

- 当前工作区；
- 当前文件类型；
- 已保存或未保存状态；
- 字符数或字数；
- 文本编码；
- 光标位置；
- DOCX 兼容状态；
- 未来 AI 服务状态。

### 6.5 Task 11 桌面外壳与信息架构实现基线

Task 11 已完成产品代码、自动质量门禁与 Windows 人工终验（见 [TASK-011 完成报告](../tasks/task-011/TASK_011_COMPLETION_REPORT.md)），并冻结以下界面实现边界：

- Electron 默认应用菜单已移除；renderer 内只保留一套中文、可测试、命令真实的应用菜单，不新增 menu IPC；
- 活动栏只展示已实现的文件与搜索入口，使用项目内 SVG、tooltip、`aria-pressed` 和明确无障碍名称；未实现设置不作为可用入口；
- 侧栏宽度 180–420 px，可通过指针或键盘调整、折叠并恢复；文件树是主要滚动区，支持长路径、深层目录与超长名称；
- 文件管理从底部按钮区迁移到根/文件/文件夹上下文菜单和键盘命令；同工作区内部拖拽只表达移动并调用既有 `relocate`，不实现复制、覆盖、跨盘或外部拖入/拖出；
- renderer 即时拒绝 no-op、自身/后代、快照同名、saving、非法目标和过期工作区；主进程继续最终裁决逐段链接、realpath、目标竞态、伴随备份与 partial failure；
- DOCX 为连续、居中、最大 820 px 的阅读/写作列，不承诺 Word 分页；工具栏通过真实宽度观察在分组命令和“更多格式”间切换；TXT 维持全高编辑器；
- 成功 mutation 使用限时可关闭 toast；错误、冲突与部分完成保持可追溯；状态栏不再长期显示 Electron 版本，运行时信息位于“关于”；
- 样式按 tokens/common/shell/workspace/document/search 分层，并提供 `forced-colors` 与 `prefers-reduced-motion` 入口。

上述界面重构未增加 `DesktopApi`、preload 或 IPC 能力，Task 9 的 stable tabId、mutationEpoch、DOCX `.wenshu.bak`、回收站与写入安全，及 Task 10 的当前 DOCX 查找替换生命周期保持为回归基线。项目所有者已于 2026-08-27 完成 Windows 物理 100%/125%/150% 显示缩放、200% 文本缩放、高对比度、减少动画与屏幕阅读器等人工终验，未发现问题。

## 7. 总体技术架构

项目采用单机桌面应用架构，初期划分为以下模块：

```text
桌面应用
├─ Electron 应用外壳
├─ React 用户界面
├─ 工作区与文件树
├─ 标签页与编辑器
├─ 文件类型处理器
├─ 搜索
├─ 设置与状态持久化
└─ AI 接口预留
```

### 7.1 Electron 应用外壳

负责：

- 用户选区；
- 工作区文件列表；

- 文本修改建议；

若未来明确需要更接近 VS Code 的纯文本体验，可以评估 Monaco Editor，但初期推荐 CodeMirror 6。

Task 4 从只读 TXT 进入编辑阶段时采用 CodeMirror 6。编辑器只维护界面内存状态，不直接访问文件系统；读取和保存继续通过 preload 与固定 IPC 的窄接口完成。

Task 5 已在不扩大文件系统权限的前提下把单文档编辑扩展为多 TXT 标签页。每个标签独立维护正文、磁盘版本、修改状态、保存状态、错误、冲突和 CodeMirror 会话；标签切换保留光标、选区、滚动位置及撤销/重做历史。多标签仍复用 Task 4 的固定读取/保存 IPC，未为 renderer 会话管理新增通用桌面能力。具体实施边界见 [TASK-005 规划](../tasks/task-005/TASK_005_MULTI_TXT_TABS.md)。

Task 6 已在 CodeMirror 会话中增加当前文件查找替换（`@codemirror/search` 直接依赖），并为工作区 TXT 搜索增加独立的主进程只读搜索能力。renderer 只提交有界查询和请求身份（requestId），不能提交工作区根或任意文件系统参数；主进程负责受控遍历、TXT 读取、固定并发 4、取消、结果上限（候选 1000 / 单文件 200 / 总匹配 2000）和错误隔离。首版搜索不建立持久索引，不写工作区；结果定位绑定 requestId、工作区 epoch、相对路径、revision 与稳定 tabId，过期只提示不覆盖正文。具体实施边界见 [TASK-006 规划](../tasks/task-006/TASK_006_TXT_SEARCH_FIND_REPLACE.md)。

Task 7 已采用 Tiptap/ProseMirror 作为 DOCX renderer 编辑会话，编辑器实例不跨 IPC；项目自有 `DocxDocumentModel` 是导入、编辑状态和导出的稳定边界（`src/shared/docx.ts` 契约 + `src/shared/docx-convert.ts` 纯转换）。TXT 继续使用 CodeMirror，通用标签生命周期通过文件类型判别联合复用（`src/renderer/lib/document-tabs.ts`），TXT 与 DOCX 的正文模型和编辑器 runtime 保持隔离。具体实施结果见 [TASK-007 完成报告](../tasks/task-007/TASK_007_COMPLETION_REPORT.md)。

Task 8 已把工作区搜索扩展为 TXT + DOCX 混合搜索与富文本结果定位（见 [TASK-008 完成报告](../tasks/task-008/TASK_008_COMPLETION_REPORT.md)）：DOCX 搜索文本的唯一语义来源是 `DocxDocumentModel` 的规范正文投影（`src/shared/docx-search-text.ts`，深度优先文本块 + 人工 `\n` 分隔，UTF-16 偏移与 ProseMirror 文本位置一致），不把 DOCX 当作 UTF-8 TXT，也不直接搜索 OOXML、Mammoth HTML 或编辑器 DOM；主进程搜索器复用受控读取器并执行总候选 1000（DOCX 200）、总并发 4（DOCX 2）、协作式取消与单文件错误隔离；结果定位经 App 实时投影校验与 DOCX 宿主同规则投影二次校验后，用 ProseMirror 公开命令（`setTextSelection` / `scrollIntoView` / `focus`）设置选区、滚动与聚焦，任何过期或映射失败只显示非破坏性提示；搜索只读，不写工作区、不建索引或缓存。

Task 10 已为 DOCX 编辑器会话增加项目自有 current-search plugin 与每标签 controller（`src/renderer/lib/docx-current-search.ts` 纯函数层 + `docx-current-search-plugin.ts` ProseMirror 插件与窄 controls）：每编辑器安装一次插件、每稳定 tabId 一个 controller，重算使用微任务单次调度 + generation 丢弃旧计算（不引入 worker/索引/防抖定时器），编辑器销毁与控制器销毁完整清理订阅；替换通过公开 transaction API 构建并复用既有 `editDocxTab` / dirty / editRevision / 保存门禁（read-only、degraded 确认、saving 中继续编辑、冲突与路径迁移语义不变），不扩大 IPC/preload 暴露面。

### 9.4 稳定性和数据安全

必须满足：

- 文件读取失败不导致整个应用崩溃；
- 保存失败后保留未保存状态；
- TXT 保存前校验磁盘内容版本，外部修改冲突需要提示且不得默认覆盖；
- TXT 优先写入目标同目录临时文件，完成写入、刷盘和关闭后再替换目标；
- TXT 替换失败不得先删除、截断或不安全覆盖原文件；
- DOCX 写入前创建备份或恢复点；
- DOCX 优先写入临时文件，成功后再替换目标；
- 删除操作进行确认；
- 所有可能丢弃未保存内容的文件切换、工作区切换和窗口关闭操作需要确认；
- 不执行 DOCX 宏和嵌入脚本；
- 渲染进程不直接拥有完整 Node.js 权限；
- 文件系统能力通过 preload 和 IPC 受控暴露。

### 9.5 可维护性

应满足：

- 使用 TypeScript；
- 开启严格或较严格的类型检查；
- 文件系统逻辑与 React 组件分离；
- 编辑器、工作区和文件处理职责分离；
- 文件类型具有独立处理模块；
- 关键纯逻辑具备基础单元测试；
- 代码通过 ESLint；
- 代码由 Prettier 统一格式；
- 重要改动通过 Git 保留恢复点。

## 11. AI 与 Agent 扩展原则

未来 AI 能力可以逐步分为：

1. **文本辅助**
   - 总结、润色、扩写、缩写和语病检查。

2. **工作区问答**
   - 搜索多个文档、汇总资料和发现内容冲突。

3. **Agent 操作**
   - 创建文件、修改文档、重命名、批量替换和整理目录。

Agent 操作必须遵守：

- 只使用应用提供的受控接口；
- 不直接获得任意磁盘访问能力；
- 修改前展示计划或差异；
- 重要修改需要用户确认；
- 修改前创建备份或恢复点；
- 修改后返回结果和错误；
- 尽可能支持撤销；
- 不因接入 AI 而改变本地文件优先原则。

## 12. 后续开发 Agent 的约束

本文档定义产品方向和技术基线。负责具体阶段的开发 Agent 可以自行完成：

- 需求细化；
- 架构和目录设计；
- 任务拆分；
- 实现顺序；
- 依赖版本选择；
- 编码；
- 测试；
- 调试；
- 重构。

开发 Agent不得在没有说明的情况下改变以下基线：

- Windows 桌面端优先；
- Electron、React 和 TypeScript 为初期主技术；
- 中央文件编辑区域为界面核心；
- 先保证 TXT，再实现基础 DOCX；
- 文件保存在普通本地文件夹中；
- 不追求完整 Word 兼容；
- 不提前开发复杂插件系统；
- 初期不引入云端和用户系统；
- AI 不得无确认覆盖用户文件；
- 优先实现简单、稳定、可运行的版本。

如果需要改变基线，应先说明：

- 当前问题；
- 建议修改；
- 收益；
- 风险；
- 新增复杂度；
- 迁移成本；
- 对现有代码和文件的影响。

由项目所有者决定是否接受。

## 13. 项目成功标准

项目初期达到以下状态即可视为完成核心目标：

1. 应用可以作为独立 Windows 桌面程序运行；
2. 用户可以打开本地文件夹作为工作区；
3. 用户可以通过文件树管理文件；
4. 用户可以通过多标签页打开和切换多个文档；
5. TXT 文件可以稳定读取、编辑、搜索和保存；
6. 基础 DOCX 可以读取、编辑和导出；
7. DOCX 保存具有备份和错误保护；
8. 用户可以搜索当前文件和工作区内容；
9. 中央编辑区域保持为主要工作空间；
10. 项目结构允许未来增加其他文件类型；
11. 项目为 AI 和 Agent 保留受控扩展接口；
12. 项目能够作为个人桌面开发和 AI 辅助开发的实践成果持续迭代。

## 14. 项目简述

> 文枢（Wenshu）是一款面向个人多文档创作与资料管理的轻量级 Windows 桌面应用。它采用类似 Visual Studio Code 的工作区、文件树和多标签页交互，并以中央文件编辑区域作为界面核心。项目初期支持 TXT 与基础 DOCX 文件的管理、阅读、编辑、搜索和保存，使用 Electron、React 和 TypeScript 开发，并通过模块化文件处理和受控本地接口，为未来扩展其他文件类型、文档分析和 AI Agent 功能保留空间。
